# Darling assessment for DaySetta (read-only audit, 2026-11-06)
Tags: [X]=executed evidence on disk (screenshot/log), [P]=prose in docs only, [V]=verified in local tree now, [U]=UNKNOWN.

## 0. Bottom line
- Darling is a real, working Darwin layer for x86_64 only. The macOS-26 port ran Apple binaries and AppKit apps, but ALL of that ran on a
  wiped x86 guest. Local tree reproduces roughly the Oct-29 state, NOT the last known-good (Nov-3) state.
- aarch64 is not supported: mldr, syscall entry, signals, thread state are x86-only. No pauth/LSE on this host makes arm64e Apple userland
  non-executable without an emulator.
- Recommendation: (b)+(c) hybrid. Keep Darling as a reference/optional "Darwin-guest" backend (already DaySetta's Layer-C fallback), mine
  designs from darlingserver/libsystem_kernel, do not adopt wholesale and do not link GPLv3 code into DaySetta.

## 2. Darwin facilities Darling implements (maturity)

  scripts/generate-rpc-wrappers.py). Mature for x86_64 pre-26; 26.x gaps patched ad hoc (stubs: restartable, exc_guard, fileport/memory
  entry RPC [P handoff 4. Hiện trạng]).

  (no seccomp; decision recorded [P] handoff). Large (bsd impl/ dirs). Quality uneven: ls fts_read/getattrlistbulk, kqueue timer re-arm,
  OFD locks needed fixing during port [P].

## 4. Version fitness / arm64 direction
- xnu-12377.121.6 (= macOS 26.5 tag) is checked out on top of upstream darling master (3780f21). macOS 26.6 BaseSystem userland ran against it
  with libsystem_kernel/libdispatch swapped via dyld "root" overrides [P handoff 4]. macOS 27 (IPSW 27.0.1 local): [U]; a Mac M2 on 27.0.1 was
  used only for tracing (handoff section 2). ADR 0001 in daysetta targets 27.
- libsystem_kernel ABI drift: Apple libSystem 26 expects new libsyscall/kernel-layer bits (kernelVersion, mach_msg2, exclaves, vm_reclaim, voucher, work_interval,
  applep ptr_munge/stack_guard/malloc_entropy per stack.c diff [V]); Darling's own libkernel_table was v4 vs Apple v5 [P]. Each OS release will drift again.
- aarch64 gap list (all [V] grep):
  * mldr: `#error TODO: aarch64` at src/startup/mldr/mldr.c:260 (setup_stack64) and :436 (load64); `#error TODO: arm` :407 (fat arch pick);
    elfcalls/threads.c:321 `#error Not implemented` (thread trampoline); loader.c:70 `#error Unsupported architecture`.
  * syscall entry: linux-syscall.S branches only __x86_64__/__i386__ (lines 7,14); mach_syscall.S:5 x86_64 only; machdep_syscall.S x86; xtrace-hooks.S:23 #error;
    bsdthread_register.c:112,177 `#error Missing assembly`. `linux-arm64.h` syscall-number header exists (premigration) but nothing consumes it.
  * emulation: __x86_64__ in 22 files vs __aarch64__ in 3 (dserver-rpc-defs.h, sysctl_sysctl.c) => essentially x86 only.
  * darlingserver: Architecture::ARM64 enum exists (src/process.cpp:100); duct-tape/src/thread.c:202-216 loads only x86_thread_state64/32 (no arm_thread_state64,
    no float state); host.c:145, misc.c:43 (`_MachineStateCount`), pthread/kern_support.c:232,379,848 (stack hint, bsdthread_create, setup_wqthread) #error.
  * commpage: mldr/commpage.c uses x86 _COMM_PAGE64_BASE; arm64 commpage layout (0x0000000FFFFFC000) + CPU feature fields not implemented.
  * signals: sigexc.c uses x86 ucontext/mcontext conversion; arm64 sigcontext<->arm_thread_state64 and ESR/exception codes would be new.
  Magnitude: new port, ~every machine-dependent file; upstream Darling has no arm64 effort I can see in-tree [V], no upstream evidence checked [U].
- arm64e/PAC/LSE on this host: /proc/cpuinfo Features = "fp asimd evtstrm aes pmull sha1 sha2 crc32 cpuid" (V): no pauth, no atomics (LSE), no lrcpc; implementer 0x50 part 0x000.
  macOS arm64e cache (cache-arm64e, 79 subcaches) uses RETAB/BLRAA/LDRAA/PACIA etc. (count in daysetta/artifacts/assessment/runtime.md; non-HINT PAC/LSE => SIGILL).
  HINT-space PACIBSP/AUTIBSP run as NOPs but RETAB, braa*, ldraa, casal/ldadd are UNDEF. Native Darling-arm64 therefore needs: a qemu-user -cpu max (TCG pauth+LSE),
  or a binary rewriter, or different hardware. Not a Darling-specific bug; applies to any approach that executes Apple arm64e code.
  Also Apple dyld arm64e fixups sign pointers with PAC at bind; shared-cache pointers pre-signed.
- x86_64 route on this host: Darling needs real x86_64 CPU; qemu-user/box64/FEX not installed; x86 machines unavailable => no live validation possible.

## 5. Conflicts / complements
- Daylight (/home/ubuntu/daylight): Mach-side WindowServer that exists only inside the Darling guest (KI-15, `server/include/daylight.h` Mach IPC only; 36 commits;
  docs/protocol.md 738 routines). Complements Darling: Darling supplied Mach IPC + launchd; Daylight supplied window/CA (bridge+canvas) [X milestones].
  Evidence that "real apps" path depended on app-side `daylight-bridge.dylib` calling renderInContext because AppKit 26 CA path (ContentLayer) failed [P handoff].
  Dock SwiftUI did not draw: blocker unresolved [P handoff Nov 3 tiếp]; glass is a compositor approximation.
- DaySetta (/home/ubuntu/daysetta): explicitly "no Darling, no Apple dyld at runtime" (VISION.md:9,38,57; ARCHITECTURE.md:171; ROADMAP.md:74,145;
  COMPONENT_MAP.md:92 "Runtime never links Darling"; MIGRATION_FROM_DAYLIGHT.md; COMPATIBILITY_SCOPE.md:62-64 lists Foundation/ObjC/libdispatch as
  "IMPLEMENTED via Darling" for T1 vs own T2). That conflicts with the owner's requirement that Darling remain an option (ARCHITECTURE.md:204 lists Darling among
  things DaySetta does not ship). Resolution: keep Darling as an alternate out-of-process backend (Layer C), not a link dependency; document that policy.
- Technical overlap: both need Mach IPC emulation + bootstrap + syscall compat; darlingserver is the closest existing prior art for the mach port/task
  layer; Daylight's protocol (SkyLight 738 routines) is the layer ABOVE and is substrate-independent if DaySetta exposes Mach-port-shaped IPC.

## 6. Options
(a) Adopt Darling fork as Darwin layer
  + fastest path to running Apple x86_64 binaries IF the lost state is recreated; proven milestones [X] Terminal/Disk Utility/hello2.
  - x86_64 only; no live x86 host; lost ~40 fixes; 138 uninitialized submodules; ties to GPLv3; every macOS release = new libsystem_kernel ABI chase;
    arm64 = full new port + needs PAC/LSE emulation on this host. Contradicts DaySetta "native Linux, no guest" thesis.
  Effort driver: reconstruct (days, per RECOVERY doc) vs aarch64 port (months, [U] estimate).
(b) Adopt selected parts inside DaySetta
  - darlingserver (Mach port/IPC/task/thread server) + duct-tape: reusable design; but it embeds real XNU ipc code (APSL) and Darling GPL glue; x86-hardcoded thread state.
  - libsystem_kernel emulation: great reference for syscall translation table (BSD->Linux), only usable if DaySetta loads Apple libSystem (current plan loads own runtime).
  - launchd: only needed for Apple daemons; DaySetta plans own bootstrap.
  License: Darling GPLv3 (LICENSE, 35,147 B, "GNU GPL Version 3"); darlingserver/mldr file headers say "part of Darling ... GPL" (server.cpp, mldr.c headers [V]).
  Linking GPLv3 into DaySetta forces DaySetta under GPLv3 (or keeping it as a separate process communicating over a socket). DaySetta has NO LICENSE/COPYING file
  (`ls -a /home/ubuntu/daysetta | grep -i licen` empty) => decision pending. Some Darling pieces are Apple APSL/Apache (xnu APSL_LICENSE; launchd Apache header) — compatible
  to include but carry their own notices; libdispatch/libpthread Apache 2.0.
(c) Reimplement selectively (current DaySetta plan)
  + clean license choice; Linux-native; arm64-capable if designed so; reuse Daylight protocol knowledge (738 routines).
  - must re-solve the long tail Darling solved (kqueue, launchd/XPC pipe v5, fileport memory entries, getattrlistbulk, OFD locks, NECP, applep), no running reference
    now; ARM PAC/LSE problem remains regardless; needs emulator or different hardware to run any Apple arm64e code.
Recommended: (c) as primary; keep (a) as documented optional backend (cheap to keep: an out-of-process guest, GPLv3 isolated); study (b) as clean-room reference
(read, don't copy) for darlingserver port/thread/workqueue semantics; extract the fix catalogue from handoff lines 86-265 into DaySetta test cases.
Risks: single-source (wiped x86 box) knowledge; unverifiable claims (WebKit, Dock, authd) lack artifacts; GPL contagion; Apple ABI drift per release.
